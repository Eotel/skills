# 返信と報告

Issue・PR のコメントやチャットで、決めたことと次にすることを相手に伝える文の形。
読み手が開発者のときを中心に書く。業務の利用者には、その人が業務や画面で使う語に合わせる。

## 語彙

読み手の分野で定着した漢語・カタカナ語で書き、和語にひらかない。

| ひらいた言い方 | 読み手の語 |
| --- | --- |
| ユーザーの答え | ユーザーの回答 |
| 作って答える | 生成して回答する |
| 運営が入れておき、会話の中で引く | 運営が登録し、会話中に参照する |
| 聞き違い、発言の最後が切れる | 誤認識、発話末尾の欠落 |
| 書き直してから、別の Issue に分けた | 修正してから、別の Issue に分離した |
| ユーザーごとに | ユーザー単位で |
| 画面で選ぶ | 画面で選択する |
| ボタンが出る、メッセージを出す | ボタンが表示される、メッセージを表示する |
| 設定を読む（システムが） | 設定を読み込む、値を参照する |
| 図形を置く | 図形を配置する |
| 履歴の版、新しい版 | 履歴のバージョン、新しいバージョン |
| 直す前、直した後 | 修正前、修正後 |

「の」を重ねた句は定着した複合語にする（ログの分析 → ログ分析、設定の変更の画面
→ 設定変更画面、Q&A の表 → Q&A 表）。読み手がその分野で使う語（tool call、
ハルシネーション、レビュー）は訳さない。

「読む」は人が本や文章を読むときに使う。システムが機械的に read・load するものは
「読み込む」と書く。その処理で使っている関数の語をそのまま使ってもよい（read する、
return する）。

言い換えるのは、比喩や造語で役割をぼかした語（[word-choice.json](word-choice.json) の
正本・台帳など）、直訳語、システムの動作に当てた日常の和語。定着した専門用語は
珍しく見えても残す。

## 読点

読点は意味の切れ目に打つ。短い主題（〜は、〜では）、短い条件（〜たら）、短い目的語の
あとには打たない。打つのは、長い主語や節のあと、並べた語句の間、逆接・理由の切れ目。

- 前: 要約は、ユーザーごとに ON にできるようにします。
- 後: 要約はユーザー単位で ON にできるようにします。

## 自分の作業と相手への依頼

- 自分の作業は、主体が読める動詞で書く（修正します）。「修正後、」と名詞にすると、
  誰が修正するのか読めない。
- 相手への依頼は「〜をお願いします」で頼む。相手の行動を「見ていただきます」
  「また見てもらいます」のように、こちらの予定の形で書かない。
- 両方を 1 文にするときは、自分の作業から依頼へつなぐ。

- 前: 一覧はこの方針で修正後、再度レビューをお願いします。
- 後: 一覧はこの方針で修正しますので、改めてレビューをお願いします。

## AI の書いた文に見える型

- 定型の感謝や予告（「コメントありがとうございます」「次の方針にします」）で始めず、
  結論の文から始める（「方針を決めました」）。
- 決めたことは短い段落に 1 つずつ書く。番号は手順に付けるほか、相手が付けた番号
  （①、②）を受けるときに使う。
- 「〜する形です」「〜する返し方です」のように「形」「〜方」で仕組みをぼかさず、
  誰が何をするかを述語で書く（「管理者が選ぶ形です」→「設定は管理者が選択します」）。
- 「当然知っているべき事実」のような評価の語で範囲を示さず、例で示す
  （「契約者数のような基本の事実」）。
- 「〜を設計しています」と作業中であることだけを述べず、決めた仕組みを書く
  （「運営が登録し、会話中に tool call で参照します」）。
- つながりが文から読めるときは、段落の先頭に「なお、」「ただ、」を置かない。
