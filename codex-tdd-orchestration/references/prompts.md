# Codex prompt templates

These are the shapes that worked in practice. Adapt the specifics; keep the structure.

## Project-local commands — discovery fallback

When the user hasn't pinned the project's test / lint / format / typecheck commands, default to the stack-appropriate set below, **and** have the Phase 0 codex confirm them on its first run. If Phase 0 reports different commands (e.g., the project uses `just test` instead of `uv run pytest`), update the Phase 1 implementer / fixer prompts before launching.

| Stack | test | lint | format check | typecheck |
|---|---|---|---|---|
| Python (uv + ruff + mypy) | `uv run pytest -q` | `uv run ruff check .` | `uv run ruff format --check .` | `uv run mypy .` |
| Python (poetry) | `poetry run pytest -q` | `poetry run ruff check .` | `poetry run ruff format --check .` | `poetry run mypy .` |
| Node (pnpm + vitest) | `pnpm test` | `pnpm lint` | `pnpm fmt:check` | `pnpm typecheck` |
| Node (bun + vitest) | `bun test` | `bun run lint` | `bun run fmt:check` | `bun run typecheck` |
| Just-driven repos | `just test` | `just lint` | `just fmt-check` | `just typecheck` |

Always run the CI-equivalent format check before push (Pitfall 5) — even when the project's `lint-all` recipe already passed locally.

## Review data carrier (reviewer → fixer)

The fixer prompt is generated by the orchestrator after the reviewer reports done. The reviewer's JSON output must reach the fixer **verbatim** (no summarizing, no reordering, no severity dropping), regardless of whether the reviewer/fixer ran as a Codex thread, subagent, or parent read-only spot check. The mechanical contract:

1. Reviewer writes JSON-only output to the chosen transport's output surface (`prompts.md` reviewer skeleton enforces "本文は JSON のみ").
2. Orchestrator captures that JSON from the output file (not from any summary).
3. Orchestrator substitutes it into the fixer prompt at a literal placeholder marker. Recommended marker: `<<<PASTE REVIEWER JSON HERE>>>` (any unmistakable placeholder works; pick one and use it consistently in your fixer template).
4. The fixer prompt's `## reviewer 指摘` section is replaced with the JSON in place of the marker.

If the reviewer's output isn't valid JSON, do not pass it to the fixer; re-launch the reviewer with a "your previous output included non-JSON text" prompt.

## Implementer prompt skeleton

```
あなたは Codex CLI で <TOPIC NAME> を **TDD で** 実装する。Claude orchestrator から委譲。

## 作業場所
<worktree path>（例: `<repo>/.worktrees/<name>` — 実際の絶対 repo パスを `<repo>` に展開）。worktree の外（親リポジトリ本体や別 worktree）には絶対 cd しない。すべて worktree 内のパスで完結。

## 全体の受け入れ目標
<global acceptance objective: "done when ..." one sentence>

## この agent の slice 目標
<slice objective: "done when ..." one sentence>

## ロードマップ上の位置
<Phase/Tn name>。前提: <verified prerequisites>。次の milestone: <next gate>.

## この agent が満たす受け入れチェック
- owner: implementer / evidence: <command or file evidence> / expected: <expected result>
- owner: orchestrator / evidence: <post-agent verification> / expected: <expected result>

## ゴール
<concrete goal in 3-5 bullets>

## 対象ファイル
実装: <files>
テスト: <test files>

## TDD 強制手順
1. RED: <test to write first>。`<test command>` で FAIL を確認
2. GREEN: <impl>
3. Refactor: <cleanup>

(**Non-behavioral refactor variant**: for renames, type-annotation-only,
formatter-only, or pure extract-no-behavior-change topics, the RED test is
a *structural assertion*, not a behavioral test. Examples: "mypy --strict
on the module passes", "identifier `OldName` is absent from `git grep`",
"`typing.get_type_hints(fn)` returns the expected signature shape",
"public surface matches a snapshot". The fixer's RED step follows the same
rule.)

## 制約
- pre-commit / hooks の skip 禁止 (`--no-verify` 不可)
- コミットはまだしない (orchestrator が後でやる)
- スコープ外: <other topic files>
- 既存テストが破壊されないこと
- <project-specific env, e.g. DYLD_LIBRARY_PATH=/opt/homebrew/lib on macOS>

## 検証
<test command>
<lint command>
<typecheck command>

## 報告
status: GREEN / RED
files_changed: [...]
test_result: <pytest summary line>
lint_result: PASS/FAIL
typecheck_result: PASS/FAIL
notes: <2-3 lines>
```

## Reviewer prompt skeleton

```
あなたは <TOPIC NAME> の **敵対的レビュアー**。コードは編集しない、読むだけ。Codex thread / subagent / parent read-only spot check のどれで実行してもよいが、author の会話や隠れた理由付けは受け取らない。

## レビュー対象
<files>

## 全体の受け入れ目標
<global acceptance objective: "done when ..." one sentence>

## この reviewer の slice 目標
<review objective: "done when ..." one sentence, usually reviewer JSON is [] or contains only actionable findings>

## ロードマップ上の位置
<Phase/Tn reviewer gate>。前提: implementer reported GREEN and orchestrator verified the expected diff shape.

## この reviewer が判定する受け入れチェック
- owner: reviewer / evidence: <diff + commands/results to inspect> / expected: actionable findings as JSON, or []
- owner: orchestrator / evidence: <valid JSON parse> / expected: reviewer output can feed the fixer verbatim

## 参考ファイル
<convention examples in the same repo>

## diff を見るには
<git diff command>

## 厳しく指摘すべき観点
1. <design observation>
2. <edge case observation>
3. <test coverage observation>
4. <convention drift observation>
5. <perf / readability observation>

## 出力
JSON 配列:
[{"file": "...", "line": <int|null>, "severity": "HIGH/MEDIUM/LOW", "issue": "...", "suggestion": "..."}, ...]
指摘 0 件なら []。本文は JSON のみ。

## 制約
- 編集禁止
- worktree 内のみ参照
- 5-15 件程度に絞る、低重要度は省略
```

## Fixer prompt skeleton

```
あなたは <TOPIC NAME> の **fixer**。reviewer が出した指摘を反映する。短い修正なら subagent、広い修正や独立履歴が必要なら Codex thread を使う。

## 作業場所
<worktree>

## 全体の受け入れ目標
<global acceptance objective: "done when ..." one sentence>

## この fixer の slice 目標
<fix objective: "done when ..." one sentence, covering HIGH/MEDIUM reviewer findings>

## ロードマップ上の位置
<Phase/Tn fixer gate>。前提: reviewer JSON was captured verbatim. 次の milestone: orchestrator re-verification.

## この fixer が満たす受け入れチェック
- owner: fixer / evidence: <test command or code evidence> / expected: HIGH/MEDIUM findings addressed
- owner: orchestrator / evidence: <post-fixer diff + focused tests> / expected: no unresolved required findings

## reviewer 指摘
<<<PASTE REVIEWER JSON HERE>>>
(orchestrator substitutes the reviewer's verbatim JSON in place of this
marker — see "Inter-codex data carrier" near the top of prompts.md)

## 対応方針
- HIGH/MEDIUM 全部対応
- LOW は判断 (理由を notes に書く)

## TDD 強制
1. RED: 先に「指摘が反映されていない状態を捕捉するテスト」を追加
2. GREEN: 実装で fix
3. <verify command>

## 制約
- pre-commit skip 禁止
- コミットはまだしない
- スコープ外ファイルを触らない

## 報告
status / files_changed / addressed_review_items / not_addressed (+理由) / test_result / notes
```

## Prompt design principles

A few things that distinguish a prompt that codex actually follows from one it ignores:

- **Worktree path stated explicitly and pinned at the top.** Codex tends to drift toward main repo cwd. Repeat the path in the constraints section too. Substitute the **actual absolute repo path** for `<repo>` (e.g. `/Users/<you>/projects/<repo-name>/.worktrees/<name>`) — see Pitfall 1 in `pitfalls.md` for why sibling-path or `/tmp/` worktrees are worse choices.
- **Out-of-scope file list is mandatory.** Without it, codex sometimes "improves" adjacent code that another parallel topic is editing.
- **Report shape is a literal template.** Free-form summaries are inconsistent and harder to verify mechanically. Pin the shape.
- **TDD steps numbered, not just labeled.** "1. RED 2. GREEN 3. Refactor" with what to do at each step. The label alone gets skipped.
- **State the negative.** "Do not commit", "Do not cd out of worktree", "Do not skip pre-commit hooks" — these are easy to forget if only positive instructions appear.
- **For fixer: paste reviewer JSON verbatim.** Don't summarize. The reviewer's exact wording is what the fixer matches against, regardless of transport.
- **Give every agent an evaluable slice objective.** Agents should receive the
  global `done when ...` objective, their own `done when ...` slice objective,
  the roadmap position, and the exact checklist lines they own. This keeps them
  moving toward the same acceptance target instead of waiting for
  micromanagement.
