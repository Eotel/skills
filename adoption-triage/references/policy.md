# 改善案の採用方針

対象は、実際の作業から出た道具・検査・skill・決まり・設定の改善案。

## 採用する

実際の失敗、遠回り、三浦さんの指摘から出た案で、同じ道具や手順を今後も使い、同じことが起こりうるもの。または、文章の決まりを検査や道具で守らせる形に置き換えるもの。変更は戻せる設定・道具・文書・skill とし、聞かずに担当を立てて進める。merge と反映は repository の決まりに従う。

夜間処理による**自動採用**はこの中でも狭い範囲に限る。会話記録で失敗から成功まで確かめられた事実（道具の使い方、パス、エラーへの対処）の追記だけで、削除や条件を緩める変更を含まないもの。共通 skill と repository・project 固有 skill のどちらも候補とする。1 晩の件数を制限し、採用ごとに取り消す手段を記録する。skill が長くなるなら短く書き直す案を人の確認に回す。

## 案の形

道具の使いにくさから出た案は、使い方を書き足すより、その道具を直す案にする（理由: 2026-10-27 に三浦さんが、使い方の事実として書いた案について「手段にするより script / tool 自体の引数/optionで対応するのはどう？」と述べた）。

- 自分たちの道具（Eotel/skills の script、`~/.cache/orca-briefs/bin`、orca-board など）は、引数・option を足すか出力を直す案にする。
- 直せない外の道具（`gh`・`bee` など）は、上流への issue の案にする。直るまでの使い方は、事実として残してよい。

## 迷う

採用の条件に当たっても、次のいずれかに当たれば台帳に記録し、採用 triage の画面で三浦さんが後で見る。作業は止めない。

- 三浦さんの使い方や好みに関わる（対話で使う設定、通知の量、進め方）。
- 同僚や他チームの作業、repository の決まりを変える。
- 費用や時間が大きい（課金、新しい外部サービス、大きな作り直し）。
- 既存の決まりと食い違う、または効果を確かめる手段がない。

三浦さんの決めごとを新たに書く・広げるもの、削除・merge・投稿など戻せない操作の条件、権限、skill の手順や script の動きを変えるものも人の確認に回す。効果が怪しいものや測定が必要なものは `empirical-prompt-tuning` で検証してよい。

記録には日時、出どころ（session・作業場）、起きた事実、案、迷う理由、採用か不採用かの推奨を残す。

## 出さない

一度きりで繰り返さないもの。振り返りでは採用と迷うものだけを示し、「0 件でも」のように選択を投げる締めを書かない。
