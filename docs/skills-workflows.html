mattpocock パイプライン

「ドメイン文書(CONTEXT.md / ADR)を共有メモリに、spec → issue → 実装 → 診断 → アーキ改善を回す」設計。左から右へ流す。

前提: リポジトリごとに最初に1回 /setup-matt-pocock-skills を実行（自動発火OFF）。 issue tracker・triage ラベル・docs 配置を確定する。これを飛ばすと後続が「tracker やラベルが分からない」状態になる。
Phase 1
構想を詰める
  • grill-me 「grill me」/ 文書なしで容赦なく質問攻め
  • grill-with-docs 用語・既存決定に照合、CONTEXT.md/ADR をその場で更新
→
Phase 2
作業に落とす
  • /to-prd 会話を PRD 化して tracker へ
  • /to-issues 縦スライス issue に分解
  • /triage 状態 machine で整理
→
Phase 3
実装する
  • tdd red-green-refactor、縦スライス
  • zoom-out 不慣れな領域を触る前に俯瞰
→
Phase 4
壊れた / 腐った時
  • diagnose 再現→仮説→修正→回帰テスト
  • improve-codebase-architecture 根が構造問題なら深化 + ADR
共有メモリ: CONTEXT.md（用語集）と docs/adr/（決定）を grill-with-docs が育て、improve-codebase-architecture / triage / to-* が参照する。 ここが回るほど後工程の精度が上がる。

mattpocock 流の流儀

setup を最初に必ず
to-issues / triage / diagnose 等は tracker・ラベル・docs 配置を前提に動く。未設定なら /setup-matt-pocock-skills。
ドメイン文書が中心
CONTEXT.md と ADR が共有メモリ。決定はその場で文書化し、却下理由も ADR に残して再提案を防ぐ。
縦スライス主義
to-issues も tdd も薄く縦に通す(tracer bullet)。横スライス(全層先作り / 全テスト先書き)は明示的に禁止。
AFK 前提
to-prd / to-issues は ready-for-agent を付け、人間の文脈なしでエージェントが拾える状態をゴールにする。
自動 vs 明示起動
setup-... と teach は自動発火OFF(slash 起動)。diagnose / tdd / zoom-out は説明文の語で自動的に立ち上がる。
診断はループから
diagnose はまず再現できる feedback loop を作る。3〜5 仮説をランク付けし、fix の前に回帰テストを書く。

計画レイヤーの選び方

plan-exec(ローカル実行計画)と to-prd / to-issues(tracker への外部化)は相反しない。レイヤーが違うので「どこに出すか」で選ぶ。

plan-exec あなたの流儀
  • 出力先: ローカル docs/exec-plans/active/...md
  • 目的: 複数ターンや複数エージェントにまたがる実装の「現在地と次の一手」を repo に置く
  • 流れ: 計画を記録 → 依頼済みの範囲を実行 → 完了時に計画を削除（結果は PR 本文、PR がなければ commit 本文へ）
  • 向き: tracker 不要・軽い・repo 内で完結
to-prd / to-issues mattpocock
  • 出力先: 共有 issue tracker（GitHub 等）
  • 目的: 外部化して AFK エージェント/チームが拾う
  • 流れ: publish → 非同期で誰かが着手
  • 向き: 追跡・ハンドオフ

決め方

  • ソロ・即実装 → plan-exec → tdd
  • 外部化 / ハンドオフ / 追跡したい → (grill →) to-prd → to-issues → 各 issue を tdd
  • 大きい issue を拾った時 → その中で plan-exec を入れ子で使う
かぶる点: 「計画の分解」を両方が持つ。同じ作業で二重管理にしないため、 tracker に載せるなら to-issues、ローカルで完結するなら plan-exec、と最初に決め打つ。

to-prd と to-issues の使い分け

  • to-prd: 会話の文脈を 1枚の PRD（spec）に。機能全体の「何を・なぜ」を固める。
  • to-issues: 計画 / PRD を 着手可能な縦スライス issue に割る。各スライスを quiz して承認後 publish。
  • チェーン: to-prd → to-issues。小機能なら to-prd 単体、方針確定済みなら to-issues 直行。
